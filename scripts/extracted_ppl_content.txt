Introduction1.1 PurposeThis Test Strategy sets out the core elements of the testing methodology that will be applied within the programme. It is intended to be a dynamic, evolving document that will be refined as delivery progresses, adapting to meet changing needs and demands.The strategy provides clear guidance throughout all phases of testing. It outlines the overall approach at a high level while also highlighting key considerations across test phases.1.2 ObjectivesThe objectives of this Test Strategy are to:Ensure Quality: Validate that all delivered solutions meet business, functional, and non-functional requirements.Enable Early Defect Detection: Testing will begin as early as possible with overlapping phases, enabling early detection of defects to reduce rework and cost.Provide Transparency: Test results, dashboards, and metrics will be generated from Azure DevOps pipelines and test plans, giving near real-time visibility.Standardized Practices: Apply consistent, auditable, and reusable testing approaches across teams, including traceability from requirements to test outcomes.Leverage Automation: Embed automated testing in CI/CD pipelines across unit, integration, system, and E2E phases, producing reusable regression suites.Support Business Confidence: Provide reliable evidence that the solution is fit for purpose and ready for release.Define Clear Responsibility and Ownership: Establish accountability for each test phase (unit, integration, system, UAT, performance, security) and environment management (dev, test, staging, production-like), ensuring clarity in roles and responsibilities.Define Tooling for Testing: Standardize on a defined set of tools for test management, automation, performance, and security testing (e.g., Azure DevOps for planning and reporting, Selenium/Playwright for automation, JMeter/K6 for performance, OWASP/ZAP for security).Acceptance Gates for Testing: Define measurable quality gates (e.g., unit test pass rate thresholds, code coverage %, defect severity thresholds, performance benchmarks) that must be met before progressing to the next test phase Test Approach2.1 Testing LifecycleTesting will follow a hybrid Agile model. Activities include planning, design, execution, defect management, reporting, and closure. Testing will integrate tightly with CI/CD pipelines.This diagram shows the different stages where testing teams are involved – each arrow represents a gate  2.2 Test Design & Planning2.2.1 Requirements & Story ReadinessTest leadership (Scrum Lead, InSprint Test lead, QA/PROD ) ensure that user stories are clear, unambiguous, and testable as standalone items, with explicit documentation of technical dependencies.Test teams contribute during detailed design by reviewing and signing off acceptance criteria, validating supporting detail (e.g., data matrix, process diagrams, screen designs), confirming APIs and dependencies, and highlighting test or test data needs.The Definition of Ready (DoR) includes test team sign-off, ensuring stories are testable before entering a sprint.2.2.2 Test Case DesignTest cases are derived from requirements, user stories, and acceptance criteria. Full traceability is maintained in Azure DevOps by linking requirements, test cases, executions, and defects.2.2.3 In-Sprint Test Planning & ExecutionAll stories are expected to be completed within a sprint; however, where this is not achievable, stories may be carried forward into the subsequent sprint. A story will not be formally closed until all Definition of Done (DoD) criteria have been fully satisfied and verified.Developers:Agree story scope and DOR / DODWrite and automate unit tests within the CI pipeline.Ensure unit tests pass before code promotion.Submit code to peer review and static analysis prior to moving into staging.Testers (embedded in scrum teams):Agree story scope and DOR / DODOwn system testing for sprint deliverables.Execute tests based on approved acceptance criteria.Perform exploratory testing alongside scripted tests, validating both “happy path” and “unhappy path” flows (including database checks and role-based access).Highlight UI defects even when APIs are mocked (not formally passable until real APIs are available).2.3 Test Levels & TypesBelow is a table showing the Testing levels/types: LevelDescriptionOwnerWhen it runsEnvTriggerResultsUnitwritten and automated by developers, validated in CI pipelines.Devsevery PRCIpush/pull_requestCI job “unit-tests” → JUnit artifacts, coverage report Azure DevOpsIn-Sprinttesters validate system functionality within sprints; Test Automation- Scope: Automate smoke, regression, and high-value repeatable tests.- Smoke Tests: Quick validation that a deployed build is stable for further testing.- Regression Tests: Ensure existing functionality continues to work after changes or fixes.- Framework: Automated tests executed through Azure DevOps pipelines, integrated with tools such as Selenium and Cypress.- Coverage: Balanced approach combining automated regression with manual exploratory testing.4. Defect ManagementWithin the scope of testing, defects are managed to ensure issues discovered during execution are properly tracked, verified, and used to strengthen future test coverage. Broader defect processes (lifecycle, prioritization, reporting) are addressed in the TOM and Service Management documentation.Defect Logging: All defects identified during testing are logged in Azure DevOps and linked to the relevant test case and user story.Verification: Once resolved, defects are re-tested; regression tests are created/updated if needed.Traceability: Test execution reports in Azure DevOps provide visibility of open defects against requirements.Continuous Improvement: Root cause insights from defects guide where new tests (unit, integration, regression) should be added to strengthen coverage.5. Entry and Exit CriteriaClear entry and exit criteria ensure that testing only begins when environments and prerequisites are ready, and that progression to the next phase occurs only once agreed quality standards have been met.10.1 Entry CriteriaTesting at each level will only start when the following conditions are met:Build Availability: Code compiled, packaged, and deployed successfully to the target environment.Environment Readiness: Required test environment provisioned, stable, and configured with relevant integrations.Test Data: Required synthetic/representative data sets loaded and available.Requirements/Test Cases: User stories or test scenarios documented, peer-reviewed, and approved in Azure DevOps.Defect Status: No open blocker defects from earlier test phases.10.2 Exit CriteriaTesting at each level will be considered complete when the following conditions are satisfied:Planned Coverage Executed: All in-scope test cases for that level executed in Azure DevOps.Defect Status:No critical/blocker defects remain open.All high severity defects triaged with resolution or agreed deferral.Results Logged: Test results published in Azure DevOps with evidence attached.Sign-Off: QA Lead (or Product Owner for UAT) has approved progression to the next environment.11. Migration Risks & Timeline
Monolithic system architecture: While AI tools can assist in extracting and cleaning the underlying C# code the resulting codebase typically reflects a monolithic architecture. This process would compromise design quality, maintainability, and adherence to best practices, potentially leading to suboptimal outcomes in the resulting system architecture. Decomposing a monolith into a well-structured set of microservices demands substantial time, effort, and architectural expertise.
Unreliable AI-generated code: Our AI experts know that new experimental AI tools cannot produce well-structured, maintainable code at the scale of an application like PPL. Outputs often include bugs which are difficult to find and are not covered with existing test packs.
Time-consuming manual rework: We have complete confidence we can develop quicker from the ground up than by trying to re-use the existing code.
Maintainability, Technical Debt & Cost
Hard to evolve: Converting the existing code retains existing poor design, duplicated logic, and anti-patterns, compounding technical debt. This results in a platform that is still difficult to improve.
Impedes internal technology team: Unworkable code and entrenched technical debt will block PPL’s ability to build in-house technology teams, and you will remain beholden to Deloitte for future development.
Increased maintenance effort: Working with poorly structured or AI-generated legacy code slows development and increases long-term costs.
Quality & Testing
Test coverage: Current code lacks unit/integration tests. A converted version will result in a continuation of highly manual test cycles. Our ground-up rebuild ensures 90%+ coverage.
Low confidence in delivery: Without test-driven development and code reviews, quality and stability remain unpredictable.
User Experience & Performance
UI/UX issues persist: Conversion won't fix existing usability, performance, or stability problems without full re-engineering.
Slow interactions: AI conversion can't optimise backend/frontend data exchange, leading to a cumbersome UI and poor user perception. The ability of data to be pushed or streamed from the server to the client without the user requesting it will be absent, as will dynamic progress and status updates to e.g. file uploading.
Scalability & Innovation Readiness
Inflexible APIs: Current platform APIs (e.g. for placements) are rigid. New AI capabilities require more flexible REST/WebSocket APIs, which can’t be retrofitted easily on legacy structures.
Innovation blocked: Features like AI-driven workflows and real-time updates can't be layered onto a legacy structure; our approach integrates them natively.

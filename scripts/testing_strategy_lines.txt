42: 1. Introduction
43: 1.1 Purpose
44: This Test Strategy sets out the core elements of the testing methodology that will be applied within the programme. It is intended to be a dynamic, evolving document that will be refined as delivery progresses, adapting to meet changing needs and demands.The strategy provides clear guidance throughout all phases of testing. It outlines the overall approach at a high level while also highlighting key considerations across test phases.
45: 1.2 Objectives
46: The objectives of this Test Strategy are to:
47: Ensure Quality: Validate that all delivered solutions meet business, functional, and non-functional requirements.
48: Enable Early Defect Detection: Testing will begin as early as possible with overlapping phases, enabling early detection of defects to reduce rework and cost.
49: Provide Transparency: Test results, dashboards, and metrics will be generated from Azure DevOps pipelines and test plans, giving near real-time visibility.
50: Standardized Practices: Apply consistent, auditable, and reusable testing approaches across teams, including traceability from requirements to test outcomes.
51: Leverage Automation: Embed automated testing in CI/CD pipelines across unit, integration, system, and E2E phases, producing reusable regression suites.
52: Support Business Confidence: Provide reliable evidence that the solution is fit for purpose and ready for release.
53: Define Clear Responsibility and Ownership: Establish accountability for each test phase (unit, integration, system, UAT, performance, security) and environment management (dev, test, staging, production-like), ensuring clarity in roles and responsibilities.
54: Define Tooling for Testing: Standardize on a defined set of tools for test management, automation, performance, and security testing (e.g., Azure DevOps for planning and reporting, Selenium/Playwright for automation, JMeter/K6 for performance, OWASP/ZAP for security).
55: Acceptance Gates for Testing: Define measurable quality gates (e.g., unit test pass rate thresholds, code coverage %, defect severity thresholds, performance benchmarks) that must be met before progressing to the next test phase or release

105: 2. Test Approach
106: 2.1 Testing Lifecycle
107: Testing will follow a hybrid Agile model. Activities include planning, design, execution, defect management, reporting, and closure. Testing will integrate tightly with CI/CD pipelines.
108: This diagram shows the different stages where testing teams are involved – each arrow represents a gate
109: 2.2 Test Design & Planning
110: 2.2.1 Requirements & Story Readiness
111: Test leadership (Scrum Lead, InSprint Test lead, QA/PROD ) ensure that user stories are clear, unambiguous, and testable as standalone items, with explicit documentation of technical dependencies.
112: Test teams contribute during detailed design by reviewing and signing off acceptance criteria, validating supporting detail (e.g., data matrix, process diagrams, screen designs), confirming APIs and dependencies, and highlighting test or test data needs.
113: The Definition of Ready (DoR) includes test team sign-off, ensuring stories are testable before entering a sprint.
114: 2.2.2 Test Case Design
115: Test cases are derived from requirements, user stories, and acceptance criteria. Full traceability is maintained in Azure DevOps by linking requirements, test cases, executions, and defects.
116: 2.2.3 In-Sprint Test Planning & Execution
117: All stories are expected to be completed within a sprint; however, where this is not achievable, stories may be carried forward into the subsequent sprint. A story will not be formally closed until all Definition of Done (DoD) criteria have been fully satisfied and verified.
118: Developers:
119: Agree story scope and DOR / DOD
120: Write and automate unit tests within the CI pipeline.
121: Ensure unit tests pass before code promotion.
122: Submit code to peer review and static analysis prior to moving into staging.
123: Testers (embedded in scrum teams):
124: Agree story scope and DOR / DOD
125: Own system testing for sprint deliverables.
126: Execute tests based on approved acceptance criteria.
127: Perform exploratory testing alongside scripted tests, validating both “happy path” and “unhappy path” flows (including database checks and role-based access).
128: Highlight UI defects even when APIs are mocked (not formally passable until real APIs are available).

239: Test Resources
240: Effective delivery of the testing strategy relies on well-structured and collaborative test resources. The programme will leverage a combination of embedded QA specialists, dedicated test teams, and business representatives to ensure that testing is both comprehensive and efficient. Test resources are drawn from PPL test teams, BIP scrum teams with embedded QA testers, and the central BIP test team.
241: Each group plays a distinct role within the lifecycle, from early in-sprint validation and automation to end-to-end and user acceptance testing. This blended approach ensures that quality is built into the solution from the outset, while also providing independent assurance at later stages. Clear ownership, accountability, and communication channels across these teams are essential to maintaining consistency, maximising test coverage, and supporting timely defect resolution.

244: 3. Test Automation
245: - Scope: Automate smoke, regression, and high-value repeatable tests.- Smoke Tests: Quick validation that a deployed build is stable for further testing.- Regression Tests: Ensure existing functionality continues to work after changes or fixes.- Framework: Automated tests executed through Azure DevOps pipelines, integrated with tools such as Selenium and Cypress.- Coverage: Balanced approach combining automated regression with manual exploratory testing.
246: 4. Defect Management
247: Within the scope of testing, defects are managed to ensure issues discovered during execution are properly tracked, verified, and used to strengthen future test coverage. Broader defect processes (lifecycle, prioritization, reporting) are addressed in the TOM and Service Management documentation.
248: Defect Logging: All defects identified during testing are logged in Azure DevOps and linked to the relevant test case and user story.
249: Verification: Once resolved, defects are re-tested; regression tests are created/updated if needed.
250: Traceability: Test execution reports in Azure DevOps provide visibility of open defects against requirements.
251: Continuous Improvement: Root cause insights from defects guide where new tests (unit, integration, regression) should be added to strengthen coverage.

434: 10. Entry and Exit Criteria
435: Clear entry and exit criteria ensure that testing only begins when environments and prerequisites are ready, and that progression to the next phase occurs only once agreed quality standards have been met.
436: 10.1 Entry Criteria
437: Testing at each level will only start when the following conditions are met:
438: Build Availability: Code compiled, packaged, and deployed successfully to the target environment.
439: Environment Readiness: Required test environment provisioned, stable, and configured with relevant integrations.
440: Test Data: Required synthetic/representative data sets loaded and available.
441: Requirements/Test Cases: User stories or test scenarios documented, peer-reviewed, and approved in Azure DevOps.
442: Defect Status: No open blocker defects from earlier test phases.
443: 10.2 Exit Criteria
444: Testing at each level will be considered complete when the following conditions are satisfied:
445: Planned Coverage Executed: All in-scope test cases for that level executed in Azure DevOps.
446: Defect Status:
447: No critical/blocker defects remain open.
448: All high severity defects triaged with resolution or agreed deferral.
449: Results Logged: Test results published in Azure DevOps with evidence attached.
450: Sign-Off: QA Lead (or Product Owner for UAT) has approved progression to the next environment.

452: Risk
453: Impact
454: Mitigation
455: Test environment instability or downtime
456: Delays in execution, false failures
457: Environment monitoring, pre-run smoke checks, fallback environment where possible
458: Test data not available or corrupted
459: Blocked test execution
460: Maintain synthetic data sets in source control; automate data refresh pipelines
461: Late or changing requirements
462: Missed coverage, rework
463: Agile ceremonies for early clarification; testers engaged during backlog refinement
464: High volume of defects in later stages
465: Increased cost and delay
466: Shift-left with unit/integration tests; run regression early in CI
467: Flaky automated tests
468: False alarms, wasted effort
469: Regularly review and quarantine unstable tests; fix root causes promptly
470: External dependency unavailable (e.g., 3rd party API)
471: Tests blocked, incomplete coverage
472: Use stubs/mocks in lower environments; coordinate JIT window with partners
473: Limited tester availability during UAT
474: Business acceptance delayed
475: Plan UAT windows early; secure business resource commitment
